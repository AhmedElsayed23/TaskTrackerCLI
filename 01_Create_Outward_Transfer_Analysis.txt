Executive Summary
CIB.OT.FT is a high-complexity, bespoke OFS orchestration routine with no direct 1:1 equivalent on TPH/IRIS. It
combines input parsing, multi-layer business validation, config-table-driven rule branching (per channel and per
customer industry), currency conversion, an idempotency cache, and post-posting auto-authorization. Migration risk
is driven less by the OFS-to-API field mapping itself and more by the amount of business logic and control (limits,
overdraft, restricted-industry posting blocks, auto-auth) currently embedded in Universe/BASIC code and config
tables rather than in T24's native validation layer.

Service Description (Business View)
"Create Outward Transfer" lets a customer or bank operator send money out of a CIB account to a beneficiary —
whether that beneficiary holds an account at CIB, at another bank locally, or at a bank abroad. It covers the everyday
"send money" journey behind channels such as internet/mobile banking, the corporate/business banking portal
(BB.MCP), branch/teller-assisted transfers (BPM), and other API-driven integrations (VOS and generic API
clients).
In plain terms, when this service is called it:
    ●     Confirms the request hasn't already been processed (protects against double-submission, e.g. a channel
          retry or network timeout causing the same payment to be sent twice).
     ● Checks whether the requesting channel or transaction type is currently allowed to transact (e.g. temporarily
          blocked channels, restricted transaction types).
     ● For certain business/corporate customers, checks whether their industry or account is subject to a posting
          restriction (e.g. a customer flagged for enhanced control who cannot self-initiate certain payments) and
          blocks the transfer with an explanation if so.
     ● Confirms the customer has enough available funds to cover the transfer — converting currency if the
          account and the transfer are in different currencies — and, depending on the channel's configuration, may
          allow the transfer to proceed into an overdraft with a hold for review rather than rejecting it outright.
     ● Validates the beneficiary's account/IBAN and correctly identifies the beneficiary's bank, intermediary bank,
          and any routing details needed to route the payment domestically or internationally (including SWIFT-style
          MT/MX name formatting for cross-border payments).
     ● Works out who pays the transfer charges (the sender, the beneficiary, or shared) and applies the correct
          commission code and amount.
     ● Submits the payment for posting in the core banking ledger and, where the channel is configured to allow
          it, automatically authorizes the transaction so the customer doesn't need to wait for a second banker to
          approve it.
     ● Sends back a clear outcome to the channel: success with a reference number, or a rejection with a specific
          reason (insufficient funds, restricted, blocked, etc.) that the channel can show to the customer.
Who uses it: retail and corporate customers initiating transfers via digital channels, and CIB staff/branch systems
initiating transfers on a customer's behalf. Typical triggers: "Send Money" / "Transfer Funds" / "International
Wire" actions in the mobile app, internet banking, the Business Banking portal, or a partner system integrating via
API.

1. Purpose
Takes a pipe-delimited (|) flat string (I.PARAM) built by the channel, parses it into ~45 fields, builds an OFS record,
and posts it to FUNDS.TRANSFER via OFS.BULK.MANAGER. Returns a pipe-delimited response (O.MSG) with
status code, FT ID, raw OFS record, paid amount, and overrides.
This is not a T24 standard API — it's a bespoke OFS orchestration wrapper. This is exactly the kind of routine that
has no direct 1:1 equivalent in IRIS APIs, so it needs careful field-by-field and rule-by-rule mapping.

Pre-processing: input is sanitized — &, /, ',', ', ", (, ), {, }, : are all replaced with safe placeholder chars (- or ^)
before parsing. This is a hidden validation/normalization layer that must be replicated in TPH/IRIS if the
same special-character handling is expected.

2.1 Fields Received But NOT Posted to the Core Ledger — Needs a Decision
The following input fields are accepted from the channel but, based on this routine's code, never make it into the
FUNDS.TRANSFER posting. For each, the migration team must explicitly decide: (a) intentionally drop it in the

new IRIS request contract, (b) discover where else it's used in T24 R20 (a routine not covered by this file) before
dropping it, or (c) it was already dead code that predates the current requirements and can be safely retired.
    ●    BOOK.DATE — parsed, no downstream reference found
    ●    PROFIT.CNTR — split into CUST/DEBT components, neither referenced again
    ●    SRC.NARR — parsed, no downstream reference found
    ●    BEN.ADDR.1, BEN.ADDR.2, BEN.ADDR.3 — beneficiary address lines parsed, never posted or used
    ●    CHARGE.IND — parsed, no downstream reference found
    ●    BEN.BK.NAME — parsed; only the BIC code (BEN.BIC.CD) actually gets posted, the bank name text
         does not
    ● BEN.BK.SORT.CD, BEN.BK.BRANCH, BEN.BK.BRN.CD — beneficiary bank routing detail fields
         parsed, never posted or used
    ● BEN.NARRATIVE — parsed but distinct from FT.NARRATIVE (which is posted) — this specific field is
         dropped
    ● CUSTOMER.SPREAD — parsed, no downstream reference found
Separately, two fields are consumed only for validation/control-flow and are correctly never posted as ledger data
— this is expected behavior, not a gap: TXN.TYPE (restriction check input) and OD.TYPE (overdraft balance-check
gate).

2A. Technical Processing Flow (Sequence)
Step-by-step execution order as implemented in CIB.OT.FT, useful for building an equivalent orchestration
sequence (e.g. BPEL/API-gateway flow) in TPH:
1. OPEN.FILES — opens all required file handles (F.ACCOUNT.RETAIL.CU.ACCT, F.COMPANY,
FBNK.NOSTRO.ACC, F.ACCOUNT, F.CURRENCY, FBNK.FUNDS.TRANSFER,
FBNK.FUNDS.TRANSFER$NAU, FBNK.CIB.API.FT, F.CIB.ONLINE.FTS, F.CIB.API.OVERRIDE,
F.ST.CIB.FI.FT.PARAM, FBNK.CUSTOMER).
2. Sanitize I.PARAM — strip/replace reserved delimiter characters so downstream FIELD() parsing is safe.
3. SAVE.MSG — parse header (SRVC.ID, CHNL.CODE, MSG.ID, TOKEN.ID), resolve per-channel override
config (CIB.API.OVERRIDE) and Business Banking industry flag (CHECK.FI.IND.UPD.FLAG /
ST.CIB.FI.FT.PARAM), parse all 51 positional fields, then read-or-create the CIB.API.FT audit/idempotency record
for this MSG.ID.
4. Idempotency gate — if CIB.API.FT already shows CUR.STATUS = 0000 for this MSG.ID, skip straight to
building the cached response (no re-validation, no re-posting).
5. Channel restriction gate (API channel only) — call CIB.API.VALIDATE.FT; if restricted, short-circuit with
status 0006.
6. FT.PROCESS — normalize SRC.ACC.ID format, compute available balance (GET.NET.AVL.BL), convert
currency if needed (GET.EQ.AMOUNT / EXCHRATE), apply overdraft/auth-flag logic.
7. Business Banking gate — if BB.FLAG is set and a posting-restriction match is found, short-circuit with status
3003 before the balance check is even evaluated.
8. Balance gate — if available balance is insufficient and no overdraft override applies, short-circuit with status
0011 (Business Banking) or 0006 (standard).
9. Build OFSRECORD — assemble the full OFS string field-by-field (see 2B below), including BIC/IBAN
resolution, commission-code derivation, and CBE reporting fields.
10. BB.MCP dry-run gate — for BB.MCP channel only, run a VALIDATE-mode OFS call first; if
ACCT.UNAUTH.OD override is returned, short-circuit with status 0011.
11. Post — call OFS.INITIALISE.SOURCE + OFS.BULK.MANAGER to submit the real (PROCESS-mode) OFS
record to FUNDS.TRANSFER.

12. Parse OFS response — extract success flag, FT.ID, and status; on success set PAID.AMOUNT and call
UPDATE.FTS.ONLINE (SMS trigger + journal).
13. Re-read FUNDS.TRANSFER (NAU or live) to fetch OVERRIDE text for the response payload.
14. Conditional auto-authorization — if channel config requires it and the record is in an auth-pending state, call
CIB.MSG.AUTHORIZE.SC.
15. UPDATE.MSG — persist final CUR.STATUS, FT.ID, OFSRECORD, PAID.AMOUNT back to CIB.API.FT
(skipped when FUNCTION.ID = VALIDATE, i.e. dry-run/enquiry calls don't overwrite the audit record).
16. Return O.MSG to caller in the format HEADER.ID|STATUS|FT.ID|OFSRECORD|PAID.AMOUNT|
OVERRIDE|.

3. Validations & Business Rules (the core of what must migrate)

3.1 Idempotency / Duplicate Message Check
    ●    Every inbound MSG.ID is looked up in CIB.API.FT table.
    ●    If a prior record exists with CUR.STATUS = '0000' (already successfully processed), the routine does not
         reprocess — it returns the cached FT ID / OFS record / paid amount from the original run.
Gap risk: IRIS APIs typically have their own idempotency-key handling — must confirm it matches this exact
"return cached success, skip reprocessing" behavior, not just "reject duplicate."

3.2 Channel-Level Restriction Check (API channel only)
    ●     If CHNL.CODE = 'API', calls external routine CIB.API.VALIDATE.FT with SRC.ACC.ID |
          CHNL.CODE | TXN.TYPE.
    ● Returns RESTRICT.FLAG / RESTRICT.DESC.
    ● If RESTRICT.FLAG = '1' → immediate reject with error 0006 + description, before any balance or posting
          logic runs.
This is a black-box external validation — its internal rules are not visible in this routine and must be independently
audited (separate service/routine).

3.3 Customer Industry-Based Posting Restriction (Business Banking)
    ●    Reads F.ST.CIB.FI.FT.PARAM keyed by first 4 chars of channel code.
    ●    Gets the debit account's customer, reads CUSTOMER.INDUSTRY.
    ●    If industry code matches a configured restricted-industry list → sets BB.FLAG = "TRUE", forces
         OD.TYPE = "N" (no overdraft allowed).
     ● If BB.FLAG = TRUE: checks customer/account POSTING.RESTRICT codes against a configured
         override list (CIB.API.OVERRIDE). If a match is found → hard reject with error 3003 and a configured
         description — transaction never reaches balance check or posting.
Gap risk: This entire industry+restriction-code rule engine is config-table-driven (ST.CIB.FI.FT.PARAM,
CIB.API.OVERRIDE) — needs to be reproduced either in TPH parameter tables or in an orchestration/pre-
validation layer in front of IRIS.

3.4 Available Balance Check
    ●    Calls GET.NET.AVL.BL to compute limit balance, lock amount, book/clear/available balance for the debit
         account.

    ●    If debit currency ≠ transaction currency, converts available balance to transaction currency via
         EXCHRATE (market code 11).
    ●    Rule: proceed only if AVAL.BALANCE >= SRC.AMT OR OD.TYPE = 'Y' (overdraft allowed).
    ●    Else → reject: 0011 if BB.FLAG = TRUE (Business Banking insufficient balance); 0006 otherwise
         (generic insufficient balance).
    ●    Both return the computed available balance in the error description.

3.5 Overdraft Authorization Flag Logic
    ●    If CHANGE.AUTH.FLAG = "YES" (from CIB.API.OVERRIDE config per channel) and
         AVAL.BALANCE < SRC.AMT: sets OD.FLAG = "Y", forces the record into an authorization-required
         state (AUTH.FLAG = "1", AUTH.FLAG.NEW = "1").
This means: certain channels are configured to allow overdraft but force a maker-checker style hold rather than an
outright reject.

3.6 BB.MCP Overdraft Charge Dry-Run Check
    ●    Specifically for channel BB.MCP: before real posting, does a VALIDATE-mode dry-run OFS call against
         the built OFS record.
    ●    If the dry-run response contains override ACCT.UNAUTH.OD → hard reject with 0011 (insufficient
         balance), even if the earlier balance check passed. This is effectively a second, stricter balance/overdraft
         gate specific to this channel.

3.7 IBAN Validation
    ●    If beneficiary account length = 29 → validated via IBANService.ValidateIBAN.
    ●    If valid → sent as IBAN.BEN; if invalid or not IBAN-length → sent as plain BEN.ACCT.NO.

3.8 Charges/Commission Rule Logic
    ●    BEN.OUR.CHARGES drives default COMMISSION.CODE when not explicitly supplied: OUR →
         DEBIT PLUS CHARGES; BEN → CREDIT LESS CHARGES; SHA → DEBIT PLUS CHARGES
    ●    Extra override: if resulting code is DEBIT PLUS CHARGES AND SRC.ACC.ID length > 12 →
         commission code is cleared entirely (blank). This is a non-obvious business rule tied to account number
         format/type.

3.9 Auto-Authorization (Maker-Checker Bypass)
    ●     After successful posting, if CHANGE.AUTH.FLAG = "YES" and AUTH.FLAG = 1 and
          AUTH.FLAG.NEW = "0": automatically calls CIB.MSG.AUTHORIZE.SC to auto-authorize the
          transaction (system-driven authorization, not a human checker).
This is a critical control to validate in TPH — confirm whether auto-auth is still config-driven per channel or
hardcoded differently.

3.10 SMS / Online FT Journal Update
    ●    On success, checks CIB.CHECK.SMS.RUN to decide whether to log the FT into CIB.ONLINE.FTS (used
         presumably for SMS notification triggers) and fires JOURNAL.UPDATE.

4. Response Contract (O.MSG)
Format: HEADER.ID|STATUS|FT.ID|OFS.RECORD|PAID.AMOUNT|OVERRIDE|

 Status Code              Meaning
 0000                     Success (FT posted)
 0006                     Generic reject — insufficient balance OR channel restriction OR OFS posting failure
 0011                     Insufficient balance — Business Banking / BB.MCP overdraft-specific variant
 3003                     Posting restricted — customer industry / posting-restriction match

Gap risk: these 4 status codes are CIB-custom, not standard T24/IRIS error codes. A full error code mapping table
is required against whatever IRIS returns natively.
